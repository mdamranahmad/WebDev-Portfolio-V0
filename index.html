01 — About

Frontend craft, backend discipline.

Most portfolios show polish or plumbing. I try to show both, because clients end up with one developer either way.

I came up through a full-stack curriculum that treated the database as the starting point, not an afterthought — schema design, relational integrity, and query performance first, interface second. That order stuck with me.

In practice, that means I don't hand you a pretty screen that falls over the first time the data gets messy. I model the entities and relationships, decide what the API contract looks like, and only then start shaping what the user actually sees and clicks.

I'm equally comfortable writing raw SQL against PostgreSQL or modeling a schema in Prisma — and on the frontend, building that data into a React interface that feels considered rather than assembled.

  • 01

    Model the data

    Entities, relationships, and constraints get sketched — usually as a real ERD — before a single component exists.

  • 02

    Build the contract

    A typed, authenticated API layer the frontend can rely on without second-guessing what comes back.

  • 03

    A React frontend that consumes that contract directly — responsive, animated with restraint, and honest about loading and error states.

Problem

Contributors needed to file and own their own issues; maintainers needed to control the workflow — without one role tripping over the other's permissions.

Approach

Two roles — Contributor and Maintainer — built directly into a JWT + bcrypt auth layer. The API runs on raw pool.query() calls against PostgreSQL rather than an ORM, so every query is explicit and easy to audit.

Result

A deployed tracker with a clean, role-checked REST API covering the full issue lifecycle:

Method Endpoint Auth
POST /api/auth/signup No
POST /api/auth/login No
GET /api/issues JWT
PATCH /api/issues/:id JWT
DELETE /api/issues/:id JWT (Maintainer)

Problem

A ticketing platform needs a schema that enforces real-world constraints — one fan, many bookings; one match, thousands of bookings — and a query layer that can answer real business questions fast.

Approach

Three tables — Users, Matches, Bookings — with explicit primary/foreign keys, mapped as a full ERD before any SQL was written. Bookings acts as the transactional junction table linking fans to fixtures at seat-level granularity.

Result

A tested suite of SQL against sample fixture data — joins, subqueries, NULL handling, aggregation, and pagination:

Field Table Purpose
fixture Matches Competing teams
match_status Matches Available / Sold Out / Postponed
seat_number Bookings Stadium seat allocation
payment_status Bookings Pending / Confirmed / Refunded

Problem

A content platform's backend needed its models, roles, and endpoints agreed on before implementation — not discovered mid-build.

Approach

Started with a written backend requirement analysis, then modeled the schema in Prisma for end-to-end type safety, and documented every endpoint as a Postman collection so the API is a contract, not a guess.

Result

A backend where the requirements doc, the Prisma schema, and the API tests all trace back to the same source of truth — the kind of discipline that keeps a project maintainable after handoff.
