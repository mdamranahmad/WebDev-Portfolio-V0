Overview

RentNest is a rental marketplace for tenants, landlords, and admins. Tenants browse and rent listings and pay online; landlords list and manage properties and incoming rental requests; admins moderate users, properties, and categories across the platform.

The backend is an Express 5 + Prisma 7 REST API on PostgreSQL. It owns the rental-request lifecycle and a Stripe subscription checkout with webhook handling. The frontend is a Next.js 16 App Router application with role-based dashboards and middleware-enforced route protection.

The two halves are deliberately separate repositories: the API is a contract the frontend consumes, rather than a bundle it is welded to.

Key features

  • Three roles — TENANT, LANDLORD, ADMIN — each with its own dashboard and navigation.
  • Rental request lifecycle: PENDING → PAYMENT_PENDING → APPROVED / REJECTED, with the property's availability tracked in step (Available → PENDING → WAITING → RENTED).
  • Stripe Checkout with signature-verified webhooks for checkout.session.completed and subscription updates or cancellations.
  • Property search and filtering, reviews, and per-user rental and payment history.
  • Route protection enforced server-side in Next.js middleware based on the JWT in an httpOnly cookie, with silent token refresh on expiry.
  • A Postman collection documenting every endpoint.

Challenges faced

  • Stripe webhooks need the raw body

    Signature verification only works against the untouched request payload, so /api/payment/webhook is mounted with express.raw() ahead of the JSON body parser.

  • Two states that had to stay in sync

    The rental request and the property's availability move together. Modelling both as an explicit state machine — instead of independent flags — removed a whole class of inconsistent records.

  • Staying logged in without long-lived tokens

    Short access tokens kept things safe but logged users out. Middleware now verifies the token and silently refreshes it via refresh-login, redirecting by role when that fails.

  • Money must not double-fire

    Stripe retries webhooks. Handlers are made idempotent and the payment is recorded before the state changes, so a retry can't charge or approve twice.

Potential improvements & future plans

  • Real-time notifications and tenant ↔ landlord messaging.
  • Saved searches with email and in-app property alerts.
  • Map-based search and richer filtering.
  • Admin analytics dashboards (occupancy, revenue, request volume).
  • Automated email receipts and renewal reminders.
  • Automated tests — unit coverage for the API and an end-to-end test of the full checkout flow.
