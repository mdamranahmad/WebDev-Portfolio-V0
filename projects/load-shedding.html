Load Shedding & Power Management System

A full-stack platform that models an electricity distribution hierarchy — planned load-shedding schedules, unexpected outage dispatch, and prepaid token recharge through bKash.

Express 5TypeScriptPrisma 7PostgreSQLRedisZodbKashNext.js
Live demo ↗ Client repository ↗

Overview

The system models power distribution the way it actually flows — Zone → Substation → Feeder → Area → House — and gives each of the four roles that touch it a different job: customers, technicians, substation managers, and zone managers.

It keeps planned load shedding and unexpected outages separate. Schedules are batch-generated and published against allocated kW, while outages are customer-reported, triaged, and dispatched to a technician — with zone managers able to review escalated reports.

On top of that sits a prepaid token recharge flow with a real bKash tokenized checkout behind it. The backend is a Node.js + Express 5 REST API on PostgreSQL through Prisma 7, with Redis holding short-lived state such as OTPs and bKash tokens. A Next.js frontend consumes the API.

Key features

  • Four-role access control (CUSTOMER, TECHNICIAN, SUBSTATION_MANAGER, ZONE_MANAGER) enforced by a role-aware auth() middleware.
  • The middleware re-validates the user's live status in the database on every request — blocked, soft-deleted, or unverified users are rejected.
  • Batch generation and publishing of load-shedding schedules against allocated kW.
  • Outage reporting → substation-manager triage → technician assignment → resolution, with zone-manager escalation review.
  • Prepaid token recharge initiated and confirmed through a bKash callback, then recorded as a payment.
  • Role-specific analytics and reporting endpoints.
  • Modular Prisma schema — one .prisma file per domain model — kept readable and easy to review.

Challenges faced

  • Preventing double-assignment

    Two outage reports could be dispatched to the same technician at almost the same time. I wrapped the assignment flow in prisma.$transaction() so it either fully succeeds or cleanly fails.

  • Keeping dispatch queries fast

    As outage data grows, the triage list slows down. Composite indexes on [reportStatus, isAssigned] and [zoneId, subStationId, areaId] keep the hot queries responsive.

  • Too many round-trips to bKash

    Re-authenticating with the gateway on every call was wasteful, so the bKash ID and refresh tokens are cached in Redis with TTLs.

  • OTP verification without a session

    During email verification there is no logged in user yet. I stored the OTP and the pending registration payload in Redis with an expiry instead of inventing a half-created row.

  • Keeping a big relational domain legible

    The schema touches 16 models. Splitting it into one file per model and standardising success/error responses kept the codebase navigable.

Potential improvements & future plans

  • Add a dedicated ADMIN role and an audit log model for critical actions such as approvals and status changes.
  • Add global rate limiting and Helmet security headers.
  • Add a POST /auth/logout endpoint and profile update endpoints (PATCH /users/me).
  • Return structured field-level validation errors (an errors: [] array) instead of a single message string.
  • Use Redis to cache expensive read queries (schedules, analytics) as well as short-lived state.
  • Make the zonal-manager approval route a PATCH for consistency with the substation-manager equivalent.
