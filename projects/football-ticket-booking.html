Football Ticket Booking System

An ERD-first relational schema and a suite of analytical SQL for tournament-scale ticketing — designed so a stadium seat can never be double-booked.

Overview

A relational database design and SQL implementation case study for a tournament-scale football ticketing platform. It models administrative and customer roles, upcoming match fixtures, and stadium seat reservations — then proves the design with a suite of analytical queries.

The deliverable is an ERD-first schema (Users, Matches, Bookings) with explicit constraints, plus the SQL that answers real business questions against sample data.

Key features

  • Three normalized tables with explicit primary and foreign keys.
  • Users (Ticket Manager / Football Fan), Matches (fixtures, tournament category, status, base price), and Bookings — the transactional junction linking a fan to a match at seat level.
  • Relationships: one fan → many bookings; one match → many bookings; and each booking row maps one user to one match for a specific seat.
  • Match status (Available / Selling Fast / Sold Out / Postponed) and payment status (Pending / Confirmed / Cancelled / Refunded).
  • A suite of queries covering joins, subqueries, aggregation, NULL handling, pattern matching, and offset pagination.

Challenges faced

  • Preventing a double-booked seat

    The whole point of the model is that a seat can't be sold twice. That meant thinking about constraints and the shape of the Bookings table up front, not patching it later.

  • Relationships that reflect reality

    Getting the cardinality right — one-to-many for purchases, but a logical one-to-one for seat allocation — required resisting the urge to over-normalise.

  • NULL handling and pagination

    Optional fields and paginated listings are where naive SQL quietly breaks. Writing those queries correctly and readably was a core part of the exercise.

  • Keeping the ERD and the SQL in sync

    As the model evolved, the diagram and the queries had to move together so they didn't tell two different stories.

Potential improvements & future plans

  • A transactional booking flow (seat locking) exposed through an API.
  • Payment gateway integration to match the payment_status field.
  • Stored procedures or triggers to enforce seat allocation rules at the database layer.
  • Indexes tuned to the hottest booking and search queries.
  • Re-implement against a Prisma-backed API so the schema and the application share one source of truth.
